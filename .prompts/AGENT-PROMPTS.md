# 个人输入分析系统：开发拆分与 Agent Prompt 包

## 1. 工程量总评估

目标范围按 **V1（P0 + P1）** 估算，包含：
- 输入记录与总览
- 基础统计分析
- 高频词 / 新词 / 词云
- 时段热力图与会话分析
- 词库管理与导出迁移
- 报告生成
- 隐私 / 保留 / 删除 / 脱敏
- 测试、集成、打包、演示

**总体工程量**：约 **27~38 人日**  
**并行开发建议**：6~8 个 coding agents  
**主线交付周期**：约 **8~12 个工作日**  
**扩展轨（P2）**：另加约 **10~16 人日**

## 2. 并行开发波次

### 第 0 波（先行）
- Agent 0：共享契约与骨架

### 第 1 波（主开发并行）
- Agent A：输入采集与会话切分
- Agent B：统计分析引擎
- Agent C：词库管理与迁移
- Agent D：Dashboard 与报告
- Agent E：隐私与数据治理

### 第 2 波（中后期）
- Agent F：测试套件与验收数据

### 第 3 波（收口）
- Agent G：集成、发布与演示

---

## 3. 模块边界与统一口径

所有 Agent 必须遵守以下统一边界：

1. 本项目是“个人输入分析系统”，不是输入法引擎替代品。
2. 默认只处理“已上屏文本”和围绕它产生的分析数据。
3. 所有功能以“本地优先、用户可删、用户可导出”为前提。
4. 一切统计口径必须支持按时间范围过滤：今天、近 7 天、近 30 天、本月、自定义、全部。
5. 所有页面和接口必须能处理空数据、历史数据不足、过滤后无结果三种状态。
6. 输出层不得假设未来一定联网或一定有云服务。
7. 各模块必须能在没有真实输入法环境的情况下，使用样例数据独立开发与验收。
8. 所有导出能力都必须考虑最小可用版本：至少可导出结构化数据与可读报告。

**开发规范**：

正确使用`git worktree`, 每个 Agent 在独立分支开发，定期 `git commit`。

## 4. Agent 0 Prompt：共享契约与项目骨架（推荐 Opus）

你负责全项目的共享契约、命名规范、模块边界和项目骨架设计。你的任务不是实现全部功能，而是给并行开发提供一套稳定、清晰、低歧义的基线，避免后续接口漂移。

### 你的目标
1. 定义全系统核心实体与字段口径。
2. 输出统一的数据契约、接口契约、目录结构、状态命名规范。
3. 为 Agent A/B/C/D/E/F/G 提供可直接依赖的基础约束。
4. 提供最小可运行骨架与样例数据，支持其他 Agent 在未联调前独立推进。

### 你必须覆盖的内容
- 输入记录事件的统一字段定义
- 会话对象定义
- 统计结果对象定义
- 高频词 / 新词 / 热词对象定义
- 词库条目对象定义
- 报告对象定义
- 设置项对象定义
- 删除 / 保留 / 导出操作的统一输入输出格式
- 页面层所需字段与接口映射
- 错误态、空态、无权限态、无数据态的统一表达

### 你的交付物
1. 项目目录骨架
2. 共享契约文档
3. 样例数据文件
4. 最小接口/服务桩
5. 模块依赖图与联调顺序说明
6. 字段字典与命名规范
7. 验收基线说明

### 非目标
- 不要深入实现复杂统计逻辑
- 不要做具体 UI 打磨
- 不要把实现细节绑死到某个框架特性上

### 验收标准
- 其他 Agent 能在不追问大量口径问题的前提下启动开发
- 契约足以支撑 P0 与 P1 主线需求
- 样例数据足以覆盖“空数据 / 普通日 / 高活跃日 / 含过滤词”几类场景

## 5. Agent A Prompt：输入采集与会话切分（推荐 Opus）

你负责“数据入口层”。你的产出决定后续统计上限。请围绕“已上屏输入记录”建立稳定的数据采集与清洗链路，并为上层分析提供可复用的事件流。

### 你的目标
1. 建立输入记录的标准化采集流程。
2. 处理记录开关、过滤规则、去噪规则和异常数据。
3. 基于时间间隔和规则完成输入会话切分。
4. 为分析层输出稳定的明细事件与会话数据。

### 你必须覆盖的内容
- 记录开关
- 暂停 / 恢复记录
- 手动忽略规则
- 敏感场景或黑名单应用忽略能力
- 明细事件标准化
- 重复输入去噪
- 空文本、纯符号、超短噪声处理
- 时间归档
- 按日切分
- 会话切分逻辑
- 为统计层准备可消费的事件流与会话流

### 你的交付物
1. 记录模块
2. 清洗与标准化模块
3. 会话切分模块
4. 可供测试与分析调用的读取接口
5. 若干代表性样例输入与对应输出结果
6. 关键边界说明

### 特别要求
- 不要假设上层一定只看当日数据
- 必须支持历史范围查询
- 要处理“同一秒多条输入”“夜间跨日会话”“记录关闭后空窗”“过滤后为空”等情况

### 非目标
- 不负责词云、热点词、新词判定
- 不负责最终报告展示

### 验收标准
- 给定一组原始记录，能稳定产出日级记录与会话分组
- 上层分析对输入源细节无感知
- 在空数据、重复数据、异常时间数据下不崩溃

## 6. Agent B Prompt：统计分析引擎（推荐 Opus）

你负责系统核心价值层。请把输入事件转化为用户真正能理解和消费的统计结果，覆盖 P0 与 P1 的大部分分析能力。

### 你的目标
1. 实现基础统计：字数、词数、条数、日/周/月趋势。
2. 实现词汇分析：高频词、新词、热词/冷词变化。
3. 实现时间分析：活跃时段、24 小时分布、热力图数据。
4. 实现会话分析：会话数量、平均会话时长、最长会话。
5. 产出面向 Dashboard 和报告的摘要结果。

### 你必须覆盖的内容
- 时间范围过滤
- 日 / 周 / 月统计聚合
- 累计统计
- 连续活跃天数
- 高频词
- 高频短语
- 新词识别
- 热词上升 / 下降
- 24 小时活跃分布
- 日期 × 时段热力图数据
- 会话统计
- 趋势对比摘要
- 报告摘要字段

### 你的交付物
1. 分析服务主模块
2. 统计聚合模块
3. 词汇分析模块
4. 时间分布与热力图数据模块
5. 会话分析模块
6. 摘要生成模块
7. 样例输入 / 输出对照
8. 边界案例说明

### 特别要求
- 结果必须能被前端直接消费，不要只输出底层原始中间结果
- 指标命名要清晰，避免语义重复
- 要考虑停用词、噪声词、极短文本对统计的污染

### 非目标
- 不负责图表绘制
- 不负责完整词库编辑交互
- 不负责保留/删除设置界面

### 验收标准
- 面向给定样例数据，能输出稳定一致的统计结果
- 统计口径在不同时间范围下逻辑自洽
- 结果足以支撑总览页、统计页、词汇页、时间页与报告页

## 7. Agent C Prompt：词库管理与迁移（推荐 Sonnet）

你负责把“分析结果”沉淀为“可管理的语言资产”。重点不是复杂算法，而是词库视图、筛选、导出与迁移体验。

### 你的目标
1. 提供个人词库总览。
2. 支持高频词、新增词、低频陈旧词、短语词的筛选与管理。
3. 提供基础清理、收藏、分类、导出能力。
4. 支持面向迁移的导出视图与迁移助手说明。

### 你必须覆盖的内容
- 词库总览指标
- 词条列表视图
- 分类筛选
- 搜索
- 排序
- 收藏 / 删除 / 忽略分析
- 标记为短语或分类词
- 导出选中词条
- 按分类导出
- 迁移助手文案与流程说明
- 低频陈旧词识别
- 高频新增词识别

### 你的交付物
1. 词库管理模块
2. 词条筛选与操作能力
3. 导出能力
4. 迁移助手所需视图/文案
5. 样例词库数据与操作结果
6. 词条状态说明

### 特别要求
- 不要把词库只做成“导出文件按钮”
- 要让用户看见词库成长与整理价值
- 导出必须考虑最低可用形式：结构化文本 / 通用词表 / 面向 Rime 的导出格式

### 非目标
- 不负责采集明细
- 不负责复杂主题画像

### 验收标准
- 用户可以浏览、筛选、整理、导出自己的词条
- 可以识别高频词、新增词、低频陈旧词
- 词库模块能独立体现“资产管理”价值

## 8. Agent D Prompt：Dashboard 与报告（推荐 Sonnet）

你负责用户最直接看到的产品层。你的任务是把复杂统计结果组织成低认知负担、高可读、具备“商业输入法分析面板”观感的总览页和报告体系。

### 你的目标
1. 完成总览页、统计页、词汇页、时间页、报告页的页面组织。
2. 把分析引擎结果转化为直观图表和指标卡。
3. 支持日/周/月报告生成与导出。
4. 保持空态、无数据态、过滤后无结果态的良好展示。

### 你必须覆盖的内容
- 首页总览卡片
- 输入趋势图
- 高频词榜
- 词云展示区
- 活跃时段图
- 热力图展示
- 会话摘要卡片
- 新词与热词变化视图
- 报告模板
- 报告导出入口
- 内容隐藏 / 脱敏展示选项
- 空态 / 无数据态 / 初次使用态文案

### 你的交付物
1. 页面结构与导航
2. 总览页
3. 统计页
4. 词汇页
5. 时间页
6. 报告页
7. 导出报告视图
8. 假数据开发模式与联调说明

### 特别要求
- 不要把页面做成单纯调接口拼图
- 要强化“少量卡片就能说明问题”的信息密度
- 所有图表都必须有标题、时间范围、单位或说明
- 用户需要能一眼读懂“今天发生了什么、最近发生了什么”

### 非目标
- 不负责底层采集逻辑
- 不负责复杂统计正确性校验

### 验收标准
- 使用样例数据即可完整走通总览、分析、报告三条路径
- 页面在空数据和低数据量时仍然可读
- 报告具备直接导出和展示价值

## 9. Agent E Prompt：隐私与数据治理（推荐 Sonnet）

你负责系统可信度和数据治理能力。请围绕“用户可知、可控、可删、可导出”构建设置中心和数据治理能力。

### 你的目标
1. 提供记录开关与记录范围说明。
2. 提供保留策略、删除策略、脱敏策略。
3. 提供黑名单、忽略名单、停用词与过滤策略管理。
4. 确保系统在数据治理上闭环完整。

### 你必须覆盖的内容
- 记录总开关
- 暂停 / 恢复
- 是否保留原文
- 是否仅保留统计
- 保留天数策略
- 自动归档策略
- 删除某天 / 某段 / 全部
- 导出前脱敏
- 黑名单应用/场景设置
- 过滤词维护
- 用户说明文案与风险提示
- 操作确认与二次确认

### 你的交付物
1. 设置中心
2. 数据治理策略模块
3. 删除与保留操作流程
4. 过滤与忽略规则配置
5. 对外可复用的治理接口
6. 关键边界测试样例

### 特别要求
- 不能只做 UI；需要形成明确的策略模型
- 删除和保留逻辑要与统计结果同步一致
- 脱敏必须考虑报告导出场景

### 非目标
- 不负责复杂统计图表
- 不负责词库迁移格式细节

### 验收标准
- 用户能明确知道记录了什么、怎么停、怎么删、怎么导出
- 删除后各类视图结果同步一致
- 治理策略不会使系统进入不可恢复的混乱状态

## 10. Agent F Prompt：测试套件与验收数据（推荐 Haiku）

你负责把系统做“稳”。你的重点不是发明新能力，而是把主线能力沉淀成可重复验证的测试与验收资产。

### 你的目标
1. 围绕 Agent 0~E 的交付构建完整测试套件。
2. 准备高质量样例数据与基准输出。
3. 覆盖功能正确性、边界情况与回归风险点。
4. 输出清晰可执行的验收清单。

### 你必须覆盖的内容
- 单元测试
- 集成测试
- 基本回归测试
- 样例输入数据集
- 基准输出快照
- 空数据场景
- 重复数据场景
- 跨日会话场景
- 过滤后无结果场景
- 删除与保留场景
- 报告导出场景
- 词库导出场景

### 你的交付物
1. 测试目录与测试脚本
2. 样例数据集
3. 快照或对照输出
4. 验收清单
5. 主要风险点列表

### 特别要求
- 测试命名要反映业务意图，而不是只反映技术实现
- 同一业务口径要被多处验证
- 要便于未来扩展到 P2 功能

### 非目标
- 不负责产品设计与 UI 改版
- 不负责底层采集集成实现

### 验收标准
- 主线流程有稳定回归保障
- 样例数据能支持本地独立验收
- 失败信息足够定位问题

## 11. Agent G Prompt：集成、发布与演示（推荐 Haiku）

你负责最后的收口，把前面模块串成完整用户路径，并交付一个可运行、可演示、可安装、可理解的版本。

### 你的目标
1. 组织端到端流程：记录 → 分析 → 展示 → 导出。
2. 处理各模块接线、默认配置、演示数据、启动方式和使用说明。
3. 交付主线 demo 与最小发布资产。

### 你必须覆盖的内容
- 模块接线
- 启动入口
- 演示数据导入
- 主线使用说明
- 最小打包方案
- 默认配置
- 错误提示与常见问题
- Demo 截图或演示流程说明
- 集成联调记录

### 你的交付物
1. 集成入口
2. Demo 配置
3. 使用说明
4. 发布说明
5. 联调问题清单与解决结果
6. 最终验收路径

### 特别要求
- 要让一个第一次接触项目的人能在最短路径内跑起来
- 不要假设使用者知道内部模块结构
- 对失败路径要给出明确提示

### 非目标
- 不负责新增复杂业务能力
- 不负责重写他人模块

### 验收标准
- 演示环境下可完整走通主线流程
- 新人可按说明复现
- 常见失败路径可定位

## 12. 推荐联调顺序

1. Agent 0 完成契约、样例数据与目录基线  
2. Agent A 输出标准化事件与会话  
3. Agent B 用 A 的样例数据跑通分析  
4. Agent D 先接假数据，再接 B 的真实输出  
5. Agent C 对接 B 的词汇结果与词库总览  
6. Agent E 接入所有“删除 / 保留 / 脱敏 / 忽略”操作  
7. Agent F 建立回归套件  
8. Agent G 完成整合、演示与打包

## 13. 可选扩展 Agent（P2）

如要启动 P2，可额外创建一个 **Opus Agent X：主题与表达画像**，负责：
- 主题分类
- 表达风格画像
- 长期兴趣变化
- 用户标签生成

此 Agent 最好等 V1 主线稳定后独立推进，避免干扰 P0/P1 主线验收。
